# `@relay/sdk` — the importable client

Relay is OpenAI-compatible, so the official OpenAI SDKs already work against it unchanged. The Relay
SDK exists for the two things those SDKs structurally cannot do:

1. **Surface Relay's own metadata.** Every proxied response carries `x-relay-provider`,
   `x-relay-cost-usd`, `x-relay-cached`, `x-relay-failover`, `x-relay-trace-id`, `x-relay-plan`. With
   `openai-node` those are buried behind `withResponse()` and untyped; here they are a typed
   `.relay` field on the result.
2. **Drive the control plane.** Applications, virtual keys, providers, routes, budgets, analytics,
   audit and plan — typed, from code, so provisioning a tenant is a script rather than clicking.

Design rationale below; the how-to lives at `/docs/sdk` in the console.

---

## 1. Principles

- **Do not reimplement the OpenAI protocol.** The data-plane client is a thin, dependency-free
  `fetch` wrapper. If you want the full OpenAI surface, keep using `openai` and point its `baseURL`
  at Relay — that path stays first-class and is what the two-line migration in the README describes.
  The Relay SDK covers the calls Relay actually mediates, and adds what Relay adds.
- **Generated, not hand-written, where a contract exists.** Control-plane types come from the
  gateway's own OpenAPI document (`api/openapi/openapi.json`, already generated by `relay openapi`)
  through the same `openapi-typescript` step the console uses. The client cannot drift from the
  server.
- **Zero runtime dependencies.** `fetch`, `AbortController` and `ReadableStream` are all standard in
  Node 18+, Bun, Deno, Cloudflare Workers and browsers. A gateway SDK that drags in a transport
  library is a gateway SDK that breaks on the edge.
- **Errors are Relay errors.** Every non-2xx is thrown as `RelayApiError` carrying the catalog
  `code`, `type` and `param` from the shared envelope — so `err.code === 'quota_exceeded'` is the
  branch, not a status-code guess.
- **The key never leaves the shape it arrived in.** No global singleton, no ambient env reading
  unless you ask for it (`Relay.fromEnv()`), no logging of the key or of prompts.

## 2. Surface

```
Relay
├── chat.completions.create(params)          → ChatCompletion & { relay }
├── chat.completions.stream(params)          → ChatCompletionStream  (+ .relay, .text(), .abort())
├── models()                                 → ModelObject[]
└── admin(token)                             → AdminClient      (control plane, Logto JWT)
    ├── me         · the token's identity and org
    ├── apps       · list create get · keys.list issue rotate revoke
    ├── providers  · list create get delete
    ├── routes     · list create get createVersion activateVersion
    ├── budgets    · list set remove setForApp removeForApp
    ├── analytics  · usage
    ├── traffic    · list get
    ├── audit      · list verify
    └── plan       · get catalog change
```

Two credentials, two clients — mirroring [ADR-0002's two auth planes](adr/0002-two-auth-planes.md).
A virtual key (`rk_live_…`) can never reach the control plane and a Logto JWT can never proxy a
completion; making that a type-level distinction in the SDK means you cannot accidentally ship an
admin token to a browser.

## 3. Data plane

```ts
import { Relay } from '@relay/sdk';

const relay = new Relay({
  baseUrl: 'https://relay.acme.internal',
  apiKey: process.env.RELAY_VIRTUAL_KEY!, // rk_live_…
});

const res = await relay.chat.completions.create({
  model: 'fast', // your alias, not a vendor's
  messages: [{ role: 'user', content: 'hello' }],
});

res.choices[0].message.content;
res.relay.provider; // 'anthropic'   — which upstream actually served it
res.relay.costUsd; // 0.000412      — metered, not estimated
res.relay.cached; // false
res.relay.failover; // true when a lower-priority target took the request
res.relay.traceId; // '8f2c…'       — the id the console's traffic view is keyed on
res.relay.plan; // 'pro'
```

`res.relay` is the whole reason the package exists. It is parsed from response headers, typed, and
`null`-safe against a gateway that predates a header.

### Streaming

```ts
const stream = await relay.chat.completions.stream({ model: 'fast', messages });

for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0]?.delta?.content ?? '');
}

const meta = await stream.relay;
// or, if you only want the finished text:
const text = await stream.text();
```

Metadata on a stream is a **promise**, not a field, because the shape of the answer depends on when
you ask. It resolves from the response headers, which the gateway must send before the first token —
so `costUsd` there reflects what was known at header time, usually `0.000000`. The settled cost lands
on the usage event and the analytics rollups. Bill from those, never from the streaming header.

### Errors

```ts
import { RelayApiError } from '@relay/sdk';

try {
  await relay.chat.completions.create({ model: 'fast', messages });
} catch (err) {
  if (err instanceof RelayApiError) {
    switch (err.code) {
      case 'budget_exceeded':
        /* the org's ceiling is reached */ break;
      case 'rate_limited':
        /* err.retryAfterSeconds */ break;
      case 'quota_exceeded':
        /* err.param names the quota */ break;
      case 'plan_upgrade_required':
        /* feature not in the plan */ break;
    }
  }
}
```

### Retries

Off by default. `new Relay({ retry: { attempts: 3 } })` retries only `429` (honouring `retry-after`)
and `502`/`503`, with jitter, and **never** retries a request that has already streamed a byte. A
gateway SDK that retries a partially-consumed completion bills you twice.

## 4. Control plane

```ts
const admin = relay.admin(await getLogtoAccessToken());

const app = await admin.apps.create({ name: 'checkout-service' });
const key = await admin.apps.keys.issue(app.id, { environment: 'live' });
console.log(key.key); // rk_live_… — returned ONCE, never readable again

await admin.budgets.set('monthly', { limit_usd: 500, hard_cutoff: true });

const plan = await admin.plan.get();
plan.limits['apps.max']; // { value: 10, source: 'plan', used: 4 }
```

`admin.plan.get()` is the same payload the console's plan page renders, so a customer's dashboard and
their provisioning script agree by construction.

### Provisioning a tenant end to end

The scenario the SDK is really for — a platform that gives each of its own customers an isolated,
budgeted slice of Relay:

```ts
const admin = relay.admin(await tokenFor(orgId));

await admin.providers.create({ name: 'openai-prod', provider: 'openai', api_key: OPENAI_KEY });
await admin.routes.create({
  model_name: 'fast',
  targets: [{ provider: 'openai', model: 'gpt-4o-mini', priority: 1 }],
});

const app = await admin.apps.create({ name: 'acme-prod' });
await admin.budgets.setForApp(app.id, 'monthly', { limit_usd: 200, hard_cutoff: true });
const { key } = await admin.apps.keys.issue(app.id, { environment: 'live' });

return key; // hand this to Acme; they point any OpenAI SDK at it
```

Onboarding the organization itself is a **platform-admin** operation (`POST /api/v1/platform/orgs`)
and is deliberately not on the tenant-scoped admin client — a tenant's token must not be able to
create tenants. Call that endpoint directly with a platform token.

## 5. Framework helpers — planned, not shipped

Not in `0.2.0`. Recorded here so the shape is agreed before anyone starts:

```ts
import { relayFetch } from '@relay/sdk/fetch'; // drop-in fetch that adds auth + parses metadata
import { withRelay } from '@relay/sdk/vercel-ai'; // Vercel AI SDK provider wrapper
import { relayPlugin } from '@relay/sdk/fastify'; // forwards trace ids, re-exports relay metadata
```

They would be optional subpath exports, so none of it lands in the base bundle. `@relay/sdk/vercel-ai`
matters more than it looks: the Vercel AI SDK is how most new TypeScript LLM code is written, and its
`createOpenAI({ baseURL })` already works against Relay — the wrapper would add the metadata plumbing
and `x-relay-trace-id` propagation. Until then, use the Vercel AI SDK against Relay directly; you
simply do not get `res.relay`.

## 6. Packaging

| Concern    | Decision                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Name       | `@relay/sdk` (npm scope reserved; published from `packages/sdk`)                                                                        |
| Build      | `tsup` → ESM + CJS + `.d.ts`, matching `packages/shared`                                                                                |
| Targets    | Node ≥18, Bun, Deno, Workers, browsers (no Node built-ins imported)                                                                     |
| Deps       | none at runtime; `@relay/shared` types are inlined at build                                                                             |
| Versioning | tracks the gateway minor (`0.2.x` SDK ↔ `0.2.x` gateway); patch releases independent                                                    |
| Types      | `paths` regenerated by `pnpm gen:api` from `api/openapi/openapi.json` — CI fails if the checked-in types differ from a fresh generation |
| Tests      | contract tests run against the real gateway in the existing compose test stack, not against mocks                                       |

### Compatibility

The SDK sends `x-relay-sdk: ts/<version>` so the gateway can report client-version spread, and
tolerates unknown response fields and missing headers — an older gateway with a newer SDK degrades to
`relay.costUsd === null`, never to a throw.

## 7. What is deliberately not in it

- **A Python SDK.** Python users already have `openai` pointed at Relay, which covers the data plane
  completely; the control plane is reachable with `requests` and the published OpenAPI spec. A second
  language doubles the release matrix for a much smaller marginal gain than the TypeScript one.
- **Prompt templating, agents, chains, evals.** Not a gateway's job.
- **Client-side key management.** The SDK will not read a virtual key from `localStorage` or accept
  one in browser code without an explicit `dangerouslyAllowBrowser: true`, for the same reason
  `openai-node` does not.
